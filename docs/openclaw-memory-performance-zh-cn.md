# OpenClaw 多实例内存评估与优化方案

## 结论与范围

2026-11-12 在 16 GiB Raspberry Pi 主机、OpenClaw 2026.11.3 上测量。当前运行 8 个 Panopticon agent、1 个独立 gateway，以及 Mission Control、语音和 VS Code。

优先减少不必要的常驻 OpenClaw 实例，其次做单实例 V8 堆上限试点。不要先压缩占用较小的 API/UI，也不要直接给全部实例套用低内存上限。以下初始测量与分阶段方案记录于 2026-11-12；后续落地和试点结果见文末。2026-11-14 的堆上限试点已撤销，未停用 agent、修改 swap 或重启主机。

## 测量结果

| 指标 | 实测 | 解释 |
| --- | --- | --- |
| 主机 MemAvailable | 初始约 3.4 GiB；配置热更新后最低约 660 MiB；对话验证后约 1.3 GiB | 不同时间点的快照，不是连续监控峰值 |

| 独立 gateway | PSS 约 682 MiB，进程 swap 合计约 313 MiB | 是否冗余需先核实独立渠道和定时任务 |

| Node 堆上限探针 | Node v24.22.2，`NODE_OPTIONS` 为空，默认堆上限约 4288 MiB | 同容器新 Node 进程探针，不是已运行 gateway 的堆使用量 |

配置更新期间 CPU、磁盘读取和内存占用上升。后续 health 容器 CPU 快照降至约 1.7%，不足以认定存在持续死循环。VS Code 也有多个高占用进程，但本次未关闭编辑器或扩展。

## 分阶段方案

### 第一阶段：减少常驻负担

1. 核实独立 `openclaw-gateway` 是否仍承担独立飞书账号或任务。如果可以停用，按本次 PSS 估计可释放约 0.7 GiB 常驻内存；交换量另计，不等同于释放 RAM。未确认前保留。
2. 选择 2–3 个确实不需要全天在线的 agent 按需启动，按当前样本粗估可减少约 2–4 GiB 常驻内存。停机期间飞书消息处理和 cron 会受影响，不能作为无损优化。必须同步调整期望服务清单与监控，不能把意外离线伪装成健康。
3. 错开索引、doctor、备份、配置热更新和重启。每次只处理一个实例，等内存与就绪状态稳定后再继续，避免九份运行时同时产生瞬时峰值。
4. 简单交互可在会话级选择较低 thinking 档位，保留复杂任务所需设置。这主要影响响应时间和模型成本，不保证明显降低本机常驻内存。

### 第二阶段：V8 堆上限单实例试点

选择一个低风险、无正在执行任务的 agent，记录原环境和回滚方式，再试验 `NODE_OPTIONS=--max-old-space-size=1024`；若真实工作负载需要更多堆，回退或评估 1536 MiB。合并既有 Node 参数，不覆盖其他参数。

- 该值只限制 V8 old space，不限制 RSS、Buffer、原生库或子进程；不能声称“容器最多占 1 GiB”。
- 生效需要重建/重启该容器，存在短暂不可用；不要九个实例同时修改。
- 对比同等空闲和工作负载的 PSS/RSS、换页、CPU、真实对话耗时；覆盖飞书、定时任务、索引和较长对话，至少观察一个日常任务周期。
- 出现 heap OOM、重启增长、持续 GC 高 CPU、明显延迟退化时，撤销参数并恢复原容器配置。
- 验证确有收益后逐个推广；2026-11-14 的短时试点未证明收益，不承诺固定降幅。
- Compose 是生成文件，持久变更应通过现有生成器/manifest 或明确维护的本地 override，不直接手改生成结果。

### 第三阶段：主机内存隔离与缓冲

1. 先确认内核具备 memory cgroup 支持及实际启动参数。在支持的 Raspberry Pi 内核上，通常需要检查 `cgroup_enable=memory`、`cgroup_memory=1` 等启动设置；具体以系统版本为准。修改需维护窗口和主机重启，本次未修改。
2. 重启后先验证 memory controller 和 `docker stats` 的非零内存统计，再依据试点峰值设置合理的容器内存/交换上限，预留 Node 非堆内存及子进程空间。
3. 可评估额外 NVMe swap 或 zram 作为 OOM 缓冲，但它们不能代替释放常驻内存；需要权衡磁盘延迟、写入量或压缩 CPU 成本，并检查既有 swap 管理服务。
4. 在可用内存不足时不要执行 `swapoff`，也不要用 `drop_caches` 伪造优化效果。评估建议目标为日常可用内存至少 3 GiB、代表性负载下无持续换页及异常重启；这不是已达成的结果。

## 2026-11-13 首批 CPU 优化落地

- 工作区 `.vscode/settings.json` 排除 agent homes、数据库数据、依赖、缓存和 runtime-assets 的文件监听、默认搜索及 Python 自动分析；业务源码和 workspace 脚本仍保留。显式导入的文件仍可能被语言服务加载，不代表彻底禁用这些目录的分析。
- 用量统计缓存默认从 15 秒延长至 60 秒，并已部署到生产 API。可设置 `MC_AGENT_USAGE_CACHE_TTL_SECONDS=15` 恢复原扫描频率；需要重建服务环境后生效。理论最大刷新频率降低 75%，不等于主机 CPU 降低 75%。
- 仅将 `personal` 的 `agents.defaults.maxConcurrent` 从 4 降至 2。OpenClaw 配置校验通过，日志确认热应用，容器未重启；其他 Agent 与子任务配置保持不变。恢复试点只需将该值改回 4。
- 备份工具的增量、全量、清理和校验命令共用 Panopticon 目录内 `.backup.lock`，避免同一目录下重叠运行。竞争时返回非零，需观察失败告警并择时重试；不会自动排队，也不能约束未使用此工具的入库和索引任务。

API 部署前确认运行源码与本次修改前源码一致，并保存旧镜像 `mission-control-api:rollback-cpu-20261113-213217`。上线后 API 地址仍为 `172.21.0.15`，就绪检查正常，实际缓存配置为 60 秒。22 项 API 健康、缓存及控制面测试、6 项备份测试通过；HTTPS 控制台及 8 个 Agent 页面正常，8 个 WebSocket 升级与握手校验通过。未重新进行模型对话测试。

短时上线后采样的 CPU 空闲约 28%–54%，换出为 0；负载与启动阶段不同，不能视为本次改动的因果收益或长期基准。后续仍需在相同任务负载下对比至少 15 分钟，并观察一个日常任务周期的排队、延迟、失败率和换页。

本轮未停用任何 Agent、修改 V8 堆上限、修改全局定时任务、限制容器 CPU 或重启主机。需保持在线的渠道不应通过停服务降占用。库存入库和索引的统一资源调度、事件级局部刷新及低频 Agent 按需启停留待后续验证。

## 控制台辅助读取降频

用量、统计摘要和容器健康读取采用进程内共享缓存，默认 15 秒。同一路径用独立锁合并并发请求，单调时钟 TTL 从请求完成时开始。任务板和活动流不缓存，原有断线重试不变。

失败结果 `None` 也短暂缓存以抑制重复请求，不复用过期的健康成功值。设置 `MISSION_CONTROL_AUX_CACHE_SECONDS=0` 可禁用；修改环境变量需重建 UI。缓存期不等于页面刷新周期，多进程之间不共享缓存。

本轮已获得用户允许，一并部署工作区现有 UI 改动。旧镜像保留为 `mission-control-ui:rollback-cpu-20261113-215238`。UI 回调测试覆盖到期、故障恢复、并发合并、禁用及既有交互，不代表已测得长期 CPU 降幅。

实际部署镜像为 `654651f484e8b3d8ca3e47599478ff0e71e8210e7e3af62799e8330e86baed1a`，镜像内 39 项 UI 回归通过，源码与资产哈希匹配。仅重建 UI，地址仍为 `172.21.0.17`，API/UI 健康且重启计数为 0。8 个 Agent 的 HTTPS 页面和 WebSocket 握手校验通过，未重新发送模型对话。

浏览器经 UI 容器地址完成渲染验收，显示 8 个 Agent、90 个任务、`Online / ws:live`；搜索无匹配时为 `0 / 90`，清空后恢复。1440px 桌面及 390px 手机宽度无页面横向溢出，观察期间未捕获脚本或 HTTP 错误。浏览器未信任本地 CA，HTTPS 证书链改用命令行显式加载项目 CA 验证，未关闭认证或改动信任配置。

最终容器 CPU 快照：UI 约 1.17%、API 约 0.11%、Agent 约 0.8%–1.3%。这些是当前运行占用，不能作为同负载前后对照或长期收益结论。

## 事件突发合并刷新

`MISSION_CONTROL_EVENT_COALESCE_SECONDS` 默认 2 秒，设置为 0 可禁用。只限制连续事件触发的整页读取频率，首次加载、60 秒安全校准和用户直接任务操作不等待该窗口；实际显示时机还受 WS tick、网络和回调耗时影响，不承诺严格 2 秒内更新。

WS 数据版本只在非 ping 事件到达时递增，只有业务读取成功才确认消费。窗口内暂缓、后续 ping 或 API 失败不会清除待处理版本；API 失败后的事件刷新遵守既有 5 秒重试间隔。该改动不修改 Agent 任务执行、消息接收和原始事件存储。

44 项 UI 回归通过。固定 10 秒内 100 个事件的同输入测试中，关闭合并时任务板与活动流共读取 200 次，启用 2 秒窗口后读取 10 次，最终数据版本均为 100。此处 95% 是测试事件流下的读取次数减少，不是主机 CPU 降幅。

已部署镜像 `d9bd54aceb9f6ddf898c92f0776312f571a45d458b14b973b7a66c84c8030401`，部署前旧 UI 镜像保留为 `mission-control-ui:rollback-events-20261113-223057`。镜像内 44 项回归通过；仅重建 UI，API 和 Agent 未重启。线上事件窗口为 2 秒、辅助缓存 15 秒，源码哈希匹配，HTTPS 返回 200。浏览器重新加载显示 `Online / ws:live`、8 个 Agent、90 个任务，数据版本字段正常，未捕获脚本错误或页面横向溢出。

## 2026-11-14 CPU 与内存复盘

### 保留的编辑器优化

本地工作区 `.vscode/settings.json` 新增 `python.analysis.indexing=false`，减少 Pylance 对未打开文件和库的后台索引。保留既有运行时目录排除，不降低类型检查级别，也不强制重启编辑器。该文件被 Git 忽略，不会随仓库部署到其他机器。

代价是未打开或未使用符号的自动导入建议减少；部分全工作区符号操作可能需要按需分析。恢复时删除该设置或改回 `true`。配置诊断通过，但尚未测得编辑器 CPU/RSS 的同负载降幅，设置改变不保证立即释放已有内存。

### 单实例堆上限试点已回滚

经用户允许，仅对 `personal` 试验 `NODE_OPTIONS=--max-old-space-size=1536`。使用临时 Compose override，部署前校验其他有效配置与镜像不变；原 `NODE_OPTIONS` 为空。实际 gateway 进程环境确认继承该值，新 Node 进程探针的总堆上限为 1728 MiB。这不是 gateway 当前堆使用量，更不是容器 RSS 上限。

| 阶段 | 可读 PSS / RSS / Swap（MiB） | 可读进程数 |
| --- | --- | --- |
| 试点前，已运行约 14 小时 | 1230.6 / 1269.7 / 206.1 | 3 / 5 |
| 1536 MiB 试点就绪后 | 1650.8 / 1776.0 / 0.0 | 3 / 5 |
| 试点稍后复测 | 1506.0 / 1585.8 / 0.0 | 3 / 5 |
| 恢复原参数后冷启动 | 1591.9 / 1729.8 / 0.0 | 4 / 6 |

测量为 `/proc/<pid>/smaps_rollup` 可读进程之和，是容器占用下界。冷启动、swap 回迁、任务和子进程数均不同，不能据此断言堆限制导致内存增加，也不能把重启前后差值称为节省。没有足够证据支持保留或推广该参数，因此已恢复原环境，并删除临时 override；没有继续试验更小上限。

试点和恢复原参数时均出现冷启动 502，随后有界重试恢复 HTTPS 200；不能仅凭容器 `running` 判断就绪。回滚命令为：

```bash
docker compose -p panopticon \
	-f panopticon/docker-compose.panopticon.yml \
	-f panopticon/docker-compose.lan-https.yml \
	up -d --no-deps --no-build --pull never --force-recreate openclaw-personal
```

最终确认 `NODE_OPTIONS` 已恢复为空或未设置，镜像未变，`personal` 地址仍为 `172.21.0.12`；异常重启计数为 0、无 OOM。8 个聊天 HTTPS 页面均为 200，`personal` WebSocket 为 101 且 accept 校验通过，飞书启动日志出现 `ws client ready`。未发送新的模型消息或飞书消息，未验证完整业务任务周期。

### 当前资源与边界

试点就绪后的 30 秒采样中，CPU 空闲约 55%–80%，swap-out 为 0，存在少量 swap-in；容器 CPU 快照为 `personal` 1.30%、UI 0.52%、API 0.19%。这是短时状态，不是本轮优化的因果收益。试点稍后主机 MemAvailable 约 2.19 GiB，2 GiB swap 仍近乎用满，尚未达到前述至少 3 GiB 可用内存的建议目标。

## 压缩、插件与持续负载优化

2026-11-14 后续用户明确要求所有 Agent 保持在线，并仅批准 `personal` 关闭 Ollama 插件试点。

### 备份压缩与优先级

`weekly-full --gzip-level 0..9` 已接入归档创建，默认从 gzip 9 级调整为 6 级。`--gzip-level 9` 可恢复原压缩级别，参数同时记录在 manifest/report 中。此变更在下次调用当前脚本时生效；没有运行真实全量备份。

固定合成数据分别包含 50,000 条 JSONL 记录，以及同一文本加 4 MiB 固定种子的不可压缩字节；每个级别交替顺序测量 3 次 CPU 时间，并逐次解压比对。以下仅为 gzip 压缩部分，不包含磁盘扫描、tar 元数据和数据库导出：

| 样本 | 9 级 CPU 中位数 / 大小 | 6 级 CPU 中位数 / 大小 | 取舍 |
| --- | --- | --- | --- |
| JSONL，5,916,661 字节 | 0.1523 秒 / 334,576 字节 | 0.0836 秒 / 431,296 字节 | CPU 约减少 45%，包体积约增加 29% |
| 混合，10,110,965 字节 | 0.2882 秒 / 4,532,014 字节 | 0.2148 秒 / 4,628,009 字节 | CPU 约减少 25%，包体积约增加 2.1% |

新生成的备份服务设置 `Nice=10`、best-effort I/O 优先级 7，与现有库存服务的低优先级一致。不强制限额、不丢任务，也不改变触发频率。本机未发现已安装的备份 user timer，本轮只在临时目录生成并通过 `systemd-analyze --user verify` 验证，未安装或启用停服备份任务。现有备份互斥锁继续保留；索引与备份之间的统一队列尚未部署。

13 项备份测试通过，新增覆盖压缩级别边界、0/3/6/9 级归档内容、权限、软硬链接、校验和、报告参数及服务优先级；Pylance 签名兼容与语法检查通过。
